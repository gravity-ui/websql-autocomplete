# Шаблонные плейсхолдеры (`{{ ... }}`)

Поддержка кастомных шаблонных плейсхолдеров (например, `{{user_id}}`) **поверх
неизменной нативной грамматики SQL**. Сгенерированные ANTLR грамматика / лексер /
парсер не трогаются — плейсхолдеры обрабатываются тонким слоем между лексером и
потоком токенов, поэтому весь нативный диалект продолжает работать как раньше.

Сейчас подключено для **MySQL**; общая механика не зависит от диалекта.

## Зачем

Редакторы запросов с шаблонизацией (в стиле dbt / Metabase / Redash / Superset)
вставляют `{{placeholder}}` внутрь в остальном валидного SQL. Если такой текст
скормить обычному SQL-парсеру, ломается лексинг/парсинг, появляются ложные
синтаксические ошибки и рушится автокомплит. Нужно, не меняя грамматику:

- чтобы плейсхолдеры в валидных позициях парсились **без синтаксических ошибок**;
- чтобы **автокомплит продолжал работать** до и после плейсхолдера;
- чтобы плейсхолдеры в реально невалидных позициях давали **валидную ошибку,
  указывающую на сам плейсхолдер** (а не на внутреннюю подстановку);
- чтобы **позиции ошибок / подсветки оставались точными** (без сдвига символов);
- чтобы плейсхолдеры внутри строковых литералов / комментариев **не трогались**.

## Публичный API (MySQL)

```ts
import {
  parseMySqlQuery,
  parseMySqlQueryWithCursor,
  parseMySqlQueryWithoutCursor,
} from '@gravity-ui/websql-autocomplete/mysql';

const {errors} = parseMySqlQueryWithoutCursor('SELECT * FROM users WHERE id = {{user_id}}', {
  supportPlaceholders: true,
});
// errors -> []
```

Все три точки входа принимают необязательный объект опций последним аргументом:

```ts
interface MySqlParseOptions {
  // Если true, `{{ ... }}` трактуются как непрозрачные значения
  // вместо синтаксической ошибки. По умолчанию: false (поведение прежнее).
  supportPlaceholders?: boolean;
}
```

Если опция не передана или `false` — поведение бит-в-бит совпадает с прежним:
слой плейсхолдеров вообще не создаётся.

## Как это устроено

### `PlaceholderTokenSource`

`src/autocomplete/shared/placeholder-token-source.ts` реализует `TokenSource` из
antlr4ng и оборачивает сгенерированный лексер. Он вставляется между лексером и
`CommonTokenStream`, поэтому парсер, antlr4-c3 и error-listener видят один и тот
же преобразованный поток.

На каждом `nextToken()` он подглядывает в поток символов **на границе токена**:

- если следующие два символа — `{{`, он сканирует до закрывающих `}}` и отдаёт
  **один** синтетический токен на весь диапазон `{{ ... }}`;
- иначе делегирует нативному `lexer.nextToken()`.

Синтетический токен:

- **маскируется** под существующий нативный тип токена (`masqueradeTokenType`),
  чтобы неизменная грамматика приняла его там, где этот тип валиден;
- несёт **точные оригинальные координаты** (offset / строка / колонка) всего
  `{{ ... }}`, поэтому позиции ошибок и подсветки не съезжают;
- сохраняет исходный текст (`{{name}}`), поэтому сообщения об ошибках ANTLR
  ссылаются на плейсхолдер, а не на внутренний тип маскировки;
- записывается в `placeholders: Map<Token, {name, start, stop}>`, чтобы
  потребители ниже по потоку (обходчики дерева, экстракторы) могли восстановить
  исходное имя.

### Почему `TokenSource`, а не альтернативы

- **Текстовый препроцессор (regex-замена)** сдвигает смещения символов → ломает
  позиции ошибок. Отклонено.
- **Склейка уже отлексированных токенов `{ { ID } }`** не работает: у лексера
  MySQL нет токенов `{`/`}`, поэтому одиночная `{` — это ошибка лексера, а не
  чистый токен. Перехватывать нужно на уровне символов.
- **Лексер-прокси, спрашивающий у парсера «какой токен здесь ожидается?»**
  ненадёжен при ALL(\*): лексер отрабатывает целиком до парсинга, а во время
  парсинга закоммиченный контекст парсера отстаёт от произвольного спекулятивного
  lookahead. Правильный инструмент для «что валидно в этой позиции» — это
  `collectCandidates(tokenIndex)` из antlr4-c3, работающий по полному потоку
  токенов (см. раздел _Расширение_).

### Безопасность строк / комментариев (бесплатно)

Перехват происходит только на границе токенов. Когда начинается строковый литерал
или комментарий, нативный лексер поглощает его целиком одним токеном, поэтому
любой `{{ ... }}` внутри просто не виден проверке на границе. Инспекция режимов
лексера не нужна.

```ts
parseMySqlQueryWithoutCursor("SELECT * FROM users WHERE name = 'hello {{user}} world'", {
  supportPlaceholders: true,
}).errors; // -> []  ({{user}} внутри строки не считается плейсхолдером)
```

## Компромисс маскировки

Так как грамматика не меняется, синтетический токен обязан переиспользовать
**существующий** тип. Для MySQL это `STRING_LITERAL` — самая широкая
value-позиция (после `=`, `IN`, `VALUES` и т.д.).

Один фиксированный тип не может быть валиден в _каждой_ позиции:

| Позиция                               | Пример                     | Результат                |
| ------------------------------------- | -------------------------- | ------------------------ |
| Значение после `=` / `IN` / `VALUES`  | `WHERE id = {{user_id}}`   | ✅ без ошибки            |
| Имя таблицы (грамматика пермиссивная) | `FROM {{table}}`           | ✅ без ошибки            |
| Внутри строкового литерала            | `WHERE name = 'a {{x}} b'` | ✅ игнорируется          |
| Только числовая позиция               | `LIMIT {{count}}`          | ❌ ошибка на `{{count}}` |
| Требуется ключевое слово              | `GROUP {{by}}`             | ❌ ошибка на `{{by}}`    |

В ❌-случаях ошибка **валидна и относится к плейсхолдеру**: её
`startColumn`/`endColumn` покрывают реальный диапазон `{{ ... }}`, сообщение
содержит текст плейсхолдера (например, `{{count}}`) и никогда не «протекает»
`STRING_LITERAL`.

Если числовые / keyword-позиции тоже должны приниматься — нужна контекстная
маскировка (см. _Расширение_).

## Тесты

`src/autocomplete/databases/mysql/tests/placeholders.test.ts` покрывает:

- **Валидные позиции парсятся без ошибок** — value-позиция, несколько
  плейсхолдеров, список `IN (...)`, плейсхолдер внутри строкового литерала.
- **Автокомплит после плейсхолдера** — keyword-продолжения (`AND`/`OR`/`ORDER`)
  после `WHERE id = {{x}} |`; подсказки таблиц для `SELECT {{col}} FROM |`.
- **Невалидные позиции дают валидную ошибку на плейсхолдере** — `LIMIT {{count}}`
  и `GROUP {{by}}`: диапазон ошибки совпадает с плейсхолдером, сообщение содержит
  текст плейсхолдера и не содержит `STRING_LITERAL`.

Запуск одного файла одним процессом с ограниченной кучей:

```bash
node --max-old-space-size=2048 --experimental-vm-modules ./node_modules/.bin/jest \
  --testPathIgnorePatterns tests/generated/.+ --runInBand \
  src/autocomplete/databases/mysql/tests/placeholders.test.ts
```

> Важно: запускать jest по одному процессу за раз. Несколько параллельных
> прогонов, компилирующих большие сгенерированные парсеры, могут исчерпать память.

## Расширение

### Другие диалекты

Общий слой не зависит от диалекта. Чтобы включить плейсхолдеры для другого
диалекта, добавьте опцию `supportPlaceholders` в `index.ts` этого диалекта и
смаппьте её в подходящий нативный тип токена (обычно — его строковый литерал),
повторив разводку MySQL.

### Контекстная маскировка (снятие компромисса)

Чтобы сделать валидными `LIMIT {{n}}`, позиции идентификаторов и т.д., выбирайте
тип маскировки для каждого вхождения, а не фиксированный:

1. лексим с плейсхолдерами как нейтральным маркером;
2. для каждого индекса токена-плейсхолдера прогоняем antlr4-c3
   `CodeCompletionCore.collectCandidates(index)` и получаем ожидаемые типы токенов;
3. выбираем тип из кандидатов (`DECIMAL_LITERAL`, если ожидается число, `ID` для
   идентификатора, иначе `STRING_LITERAL`); если value-подобного ничего не
   ожидается — оставляем так, чтобы получить корректную ошибку.

Это разрешается слева-направо и переиспользует уже имеющуюся в движке механику c3.
Это и есть правильная, принципиальная версия ответа на вопрос «валиден ли
плейсхолдер здесь?».

### Восстановление имён плейсхолдеров

`PlaceholderTokenSource.placeholders` сопоставляет каждый синтетический токен с
`{name, start, stop}`. Обходчик дерева / экстрактор может использовать это, чтобы
восстановить `{{user_id}}` обратно в `user_id` (например, чтобы пропускать
плейсхолдеры при сборе имён таблиц или колонок).
